## 一、核心结论

**JWT 像防伪门票，Redis 像门口的“作废名单/登记册”。**

面试官不是笑你用 Redis，而是笑你只会说“Token 放 Redis”，却说不清：

- 为什么放？
- 放了解决什么问题？
- 代价是什么？
- 什么场景根本不需要放？

一句话判断：

> **需不需要让已经发出去的 Token 立刻失效？**  
> 需要 → 用 Redis；不需要 → 纯 JWT 就够。

---

## 二、JWT 是什么

JWT 是一张“防伪门票”：

- 票上写着用户身份、过期时间等信息。
- 票自带签名，服务端验签即可判断是否伪造。
- 服务端**只看票本身**，不用查数据库/Redis。

优点：快、省事、无状态。  
缺点：票一旦发出，在过期前默认有效，**不擅长临时反悔**。

纯 JWT 做不到立刻：

- 作废被盗 Token
- 封号后马上拦截
- 改密码后让其他设备下线

所以纯 JWT 的弱点不是“不安全”，而是：  
**不擅长主动吊销已发 Token。**

---

## 三、Redis 的两种用法

| 方案 | 比喻 | 做法 | 特点 |
|---|---|---|---|
| Redis 黑名单 | 作废名单 | 平时空着，退出/封禁时把 Token 写入黑名单，并设置剩余过期时间 | 查询快、能主动踢人、多数业务选这个 |
| Redis 白名单 | 有效票登记册 | 所有有效 Token 都存 Redis，每次请求都查 | 控制力强，可看在线设备、限制多设备；但每次依赖 Redis，更像传统 Session |

关键区别：

- **黑名单**：默认信任 JWT，只查“是否被作废”。
- **白名单**：不完全信任 JWT，每次都查“是否登记有效”。

如果嘴上说用 JWT，结果每次请求都查 Redis 白名单，本质上更像 Session。  
不是不能用，而是要知道自己在做取舍。

---

## 四、双 Token 是什么

像两张票：

- **AccessToken**：短票，如 30 分钟，用来访问接口。
- **RefreshToken**：长票，如 7 天，只用来换新的短票。

短票过期，用长票换新，用户无感。  
长票存 Redis，改密码时删掉长票，其他设备下次就登不上。

适合：App 登录、自动续期、改密码踢设备。

---

## 五、什么时候必须用 Redis

共同点：**票已发出，但业务想临时反悔。**

1. **后台管理系统**：员工离职、管理员踢人、账号被盗。
2. **电商/社交/内容平台**：封号、改密码下线其他设备、退出所有设备、异地登录踢设备。
3. **金融/支付/企业系统**：安全要求高，强制下线、风控冻结、限制设备。
4. **限制同时在线设备数**：如视频会员最多 3 台，适合白名单。
5. **短 Token + 自动续期**：RefreshToken 存 Redis，改密码删除。

对应方案：

- 只需要主动吊销 → **JWT + Redis 黑名单**
- 还要限制在线设备数/查看在线状态 → **Redis 白名单**

---

## 六、什么时候不需要 Redis

纯 JWT 就够，别为了“高级”硬加 Redis。

1. **跨服务调用**：网关验签后传用户信息，下游直接取 userId。
2. **一次性凭证**：邮箱验证、密码重置、临时分享、邀请链接。
3. **安全要求不高的内部小工具**：用户少，不需要踢人/封号。
4. **只做登录鉴权，不做会话管理**：只关心请求是否合法，不关心设备在线状态。

---

## 七、面试答题模板

> 先看业务需不需要主动吊销 Token。  
> 如果不需要，纯 JWT 就够，服务端验签后直接从票里取用户信息，不查 Redis。  
> 如果需要封号、踢下线、改密码让其他设备失效，纯 JWT 做不到立即吊销，我会用 JWT + Redis 黑名单：正常请求验签，退出或封禁时把 Token 写进黑名单并设置剩余过期时间，请求时先查黑名单。  
> 如果还要限制同时在线设备数，那就用白名单，把 Token 存 Redis，但这样每次请求都依赖 Redis，本质上更接近 Session。

核心表达：

> **不是“Token 不能放 Redis”，而是要知道为什么放。**  
> 纯 JWT 胜在快、无状态；Redis 胜在能主动作废。  
> 面试官想听的是取舍，不是站队。

---

## 八、最简记忆版

- **JWT**：防伪门票，自己证明自己。
- **纯 JWT**：进门快，但过期前很难临时作废。
- **Redis 黑名单**：作废名单，踢人时写入，进门查一下。
- **Redis 白名单**：有效票登记册，控制强，但每次都查。
- **双 Token**：短票进场，长票换短票，长票存 Redis 可控。
- **判断标准**：要不要主动让已发 Token 失效？要 → Redis；不要 → 纯 JWT。
- **面试雷区**：只说“Token 放 Redis”，不说业务需求和方案边界。
