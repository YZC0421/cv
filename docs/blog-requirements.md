# 博客系统需求提案

> 基于当前仓库事实（Astro 5 静态站、`base: /cv`、GitHub Pages、1 篇博文 / 9 篇论文 / 7 个项目 / 9 段经历）做的产品发现，不是通用博客功能清单。

## 0. 结论先行

1. **现在缺的不是功能，是第 2 到第 6 篇内容。** 唯一一篇博文写的是"这个站点怎么搭起来的"，之后没有新内容进来。
2. **工程纪律很强，但保护的是"结构"，不是"读者体验"。** 已有 Zod schema、40 余条构建断言、`validateRelations` 在首页抛错阻断构建；但正文里的站内链接、锚点、图片资源没有任何校验，写错就是线上 404。
3. **语言处理目前是"声明式"的，不是"事实式"的。** 同一篇文章在 `/blog/x/` 与 `/zh/blog/x/` 各生成一份，互相声明为对方的翻译版本；`/zh/blog/` 与 `/blog/` 也都不按 `lang` 过滤。这不是"缺功能"，是**给出了错误信息**。

所以下面 15 个想法里，优先选的两类：让第三篇文章更快出现；不让已有内容说谎。

## 1. 现状盘点（只列与需求相关的）

| 维度 | 事实 | 位置 |
| --- | --- | --- |
| 内容体量 | blog 1 篇、publications 9 篇、projects 7 个、work 9 条 | `src/content/` |
| 语言 | 文章有 `lang` 字段，但中英文列表页都渲染全部文章 | `src/pages/blog/index.astro`、`src/pages/zh/blog/index.astro` |
| 重复页 | 每篇文章在两个前缀下各生成一份 | `src/pages/blog/[slug].astro`、`src/pages/zh/blog/[slug].astro` |
| hreflang | 由路径前缀互换推导，不检查译文是否存在；`canonical` 指向自身 | `src/i18n/utils.ts`、`src/layouts/BaseLayout.astro` |
| RSS | 单文件，`<language>` 硬编码 `zh-CN`，包含中英全部文章，链接固定走英文路径 | `src/pages/rss.xml.ts` |
| 更新日期 | `updated` 在 `blogSchema` 中存在，但文章页从不渲染，RSS/sitemap 也不用 | `src/lib/schema.ts`、`src/layouts/PostLayout.astro` |
| 渲染能力 | 无公式、无图表、代码块只有复制按钮；正文 `overflow-wrap: anywhere` 会切断英文长词与 URL | `astro.config.mjs`、`src/styles/global.css` |
| 草稿 | `visiblePosts` 无条件过滤 `draft`，本地开发也看不到草稿 | `src/lib/posts.ts` |
| 搜索 | Pagefind 仅在 `build` 后生成；无语言/分类过滤；开发环境搜索必然为空 | `src/pages/search.astro`、`package.json` |
| 分享图 | 全站共用一张 `og.png` | `src/layouts/BaseLayout.astro`、`scripts/make-og.mjs` |
| 交叉引用 | `publications ↔ work` 有关系校验并在首页抛错；`blog` 与论文/项目之间没有任何关联字段 | `src/lib/relations.ts` |

两个容易忽略的小问题：

- `scripts/verify-build.mjs` 枚举博文时只认 `*.md`，而内容集合的 glob 是 `**/*.{md,mdx}`。加第一篇 `.mdx` 后，草稿隐藏断言会静默跳过。
- `PostLayout` 把 `post.data.lang` 直接传给 `<html lang>`，所以 `/zh/blog/<英文文章>/` 会出现"URL 是中文前缀、文档语言是英文"的页面。

## 2. 机会定义

- **产品**：个人技术博客，本质是简历与论文的"解释层"。
- **目标**：把存量学术资产与工程经验转成可检索、可引用、能被读完的内容；同时把写作的边际成本压到接近 0。
- **读者**：① 招聘方/合作者，10 分钟内判断深度；② 同领域工程师/研究者，从搜索进入，需要能跑通的细节；③ 半年后的自己，需要能复用的笔记。
- **可观测的成功信号**（不依赖埋点）：
  - 文章数 ≥ 6，其中 `paper-reading` 分类 ≥ 2；
  - 每篇文章至少被 1 个项目或 1 篇论文引用（站内入链 ≥ 1）；
  - 发布前的构建检查从未因坏链接失败过（说明门禁生效而不是被绕过）。

### 机会树

```text
结果：读者 10 分钟内判断深度；作者能持续产出
├── A 存量资产没被解释      → P1 论文笔记绑定 · P2 系列 · P3 项目↔文章
├── B 开始写太贵            → E4 写作流水线（含草稿预览）
├── C 表达力不够            → E3 公式/图/代码 · D4 代码块
├── D 语言与分发不匹配       → D1 语言边界 · P4 分语言 RSS
└── E 坏页没人拦            → E1 正文链接门禁
```

## 3. 三视角想法池（15 条）

### 产品经理视角（业务价值 / 战略 / 读者影响）

- **P1 论文笔记 ↔ 论文条目双向绑定**
  让每篇笔记声明它写的是哪篇论文（DOI 或 publication id），论文列表对应条目出现"笔记"入口。解决"9 篇论文没有一个字的中文解释"。
- **P2 系列与学习路径**
  用 `series` + `seriesOrder` 把散篇组织成有顺序的课程，系列页显示总时长与进度。解决长文写不动、读者读完不知道下一站。
- **P3 文章与项目互证**
  项目 frontmatter 增加 `posts: []`，项目页列"相关文章"，文章页反链"所属项目"。解决项目页只有 goal/architecture 三行摘要、深度无处安放。
- **P4 分语言分发与首发标注**
  `/rss.xml` 与 `/zh/rss.xml` 分开，文章可声明 `syndication`（掘金/知乎/dev.to）并显示"本文亦发布于 X"。解决中文订阅者被英文条目打断、转载无回链。
- **P5 内容保鲜**
  渲染 `updated` 与 `changelog: [{date, note}]`，sitemap `lastmod` 取更新日。解决技术教程半年后失效、读者不知道还适不适用。

### 设计师视角（体验 / 可用性 / 情绪）

- **D1 语言切换讲真话**
  没有对应译文时不显示切换器，或明确标注"暂无英文版"；`hreflang` 只声明真实存在的版本。解决"点了 EN 还是这篇中文"的失信感。
- **D2 中文长文排版**
  在 CJK 与拉丁/数字边界提供视觉留白（优先 `text-autospace`，不支持的浏览器自然降级），修正 `overflow-wrap: anywhere` 导致英文单词被任意截断的问题。解决中文为主的站点里，中英混排段落"看着累"。
- **D3 阅读位置与锚点**
  顶部细进度条 + 目录高亮当前章节 + 标题悬停显示 `#` 复制锚点。解决 3000 字技术文读到一半失去位置感。
- **D4 代码块可读性**
  支持文件名标签、超过 40 行默认折叠、移动端横向滚动提示。解决现有"只有 Copy 按钮"在长代码面前不够用。
- **D5 空状态与首次访问**
  只有 1 篇文章时列表页给出"按分类浏览 / 订阅 / 从论文笔记开始"；开发环境搜索页明确说明"索引在构建后生成"。解决空列表与空搜索框造成的"这站没人维护"印象。

### 工程师视角（技术可能性 / 数据杠杆 / 可扩展）

- **E1 正文链接、锚点、资源门禁**
  构建产物里解析站内 `href`/`src`，校验目标文件、`#id`、`public/` 资源是否存在，失败即阻断。解决"构建成功但线上 404"。已有 `verify-build` 的模式可以直接复用。
- **E2 每篇文章独立 OG 图**
  构建期用现有 `sharp` 把标题/分类/日期渲染成 1200×630 PNG，注入 `og:image`。解决分享到微信/Twitter 时永远是一张统一头像。
- **E3 技术写作渲染能力**
  KaTeX 公式（CSS 本地打包）、Mermaid 图表、代码块文件名与行高亮。解决时序/LLM/论文阅读三类文章"没有公式和图就写不深"。
- **E4 写作流水线**
  `npm run new` 生成合法 frontmatter + 中文标题手动 slug；`dev` 下草稿可见并带横幅、`build` 排除；发布前跑 `summary ≤ 160`、标签 kebab-case、日期合法等检查。解决"想写 → 能发"之间的摩擦。
- **E5 内容图谱与搜索元数据**
  标签同义词表（`astro` / `astro-5`）、文章间 `[[slug]]` 自动反链、Pagefind 增加 `lang`/`category` 过滤并本地化搜索 UI。解决文章到 20 篇后列表页失效。

### 1. 写作流水线：从"想写"到"能发"不超过 3 条命令

**一句话**：把新建文章、草稿预览、发布前校验收进一个脚本，让摩擦从"查 README 抄 frontmatter"降到一条命令。

**为什么选**
内容供给是当前唯一真正的瓶颈。站点已经为此付出了成本：README 用整整一节讲怎么加文章，`summary ≤ 160`、标签 kebab-case 这些规则只有构建失败时才会被记住；写草稿必须先保持 `draft: false` 才能预览，等于在本地也承担"误发布"风险。

**范围**
- `npm run new -- "标题" --lang zh --category llm-engineering --slug some-slug`：生成 `src/content/blog/<slug>.md`，`draft: true`，frontmatter 通过现有 `blogSchema`；slug 冲突时报错退出。
- 中文标题无法自动转 kebab，`--slug` 必填；不填则从标题的拉丁字符推导，推导为空时提示。
- `visiblePosts` 增加开发态分支：`import.meta.env.DEV` 时包含草稿，页面顶部渲染"草稿"横幅（`noindex`）。
- `build` 行为不变：草稿不出现在列表、文章页、RSS、sitemap。
- `npm run post:check`：校验 `summary` 长度、标签格式、日期不晚于今天、`id` 与文件名一致。

**不做**
自动配图、自动摘要、AI 代写。这些会让"内容可信"这个唯一资产贬值。

**验收标准**
- 从空目录到本地看到渲染后的草稿，命令数 ≤ 3。
- `npm run build` 后 `dist/` 中 grep 不到草稿 slug。
- 故意把 `summary` 写到 200 字，`post:check` 退出码非 0 并指出文件。

**关键假设**
作者不写的原因主要是启动摩擦，而非没有素材或没有时间。验证方式：先上线脚本，看两周内是否能产出第 2 篇；若仍不写，说明瓶颈在选题（则转向 P1/P2）。

**工作量**：S（≤ 0.5 天）

### 2. 语言是一等公民：不生成不存在的翻译

**一句话**：只生成文章真实语言的规范路径，另一种语言要么有真译文、要么明确说"没有"，同时把 RSS 按语言拆开。

**为什么选**
这是当前唯一会主动误导读者与搜索引擎的问题：
- `/blog/` 与 `/zh/blog/` 都列出全部文章，中文读者在英文列表里看到中文标题；
- 每篇文章在两个前缀下各生成一份，`hreflang` 互相指向，`canonical` 指向自己；
- `PostLayout` 按文章 `lang` 设置 `<html lang>`，于是 `/zh/blog/<英文文>/` 的文档语言是英文；
- RSS 只有一份、`<language>` 固定 `zh-CN`、链接固定走英文路径。

对个人博客来说，"看起来有英文版，点进去还是中文"比"没有英文版"伤害更大——它直接削弱"专业可信"这个核心资产。

**范围（推荐方案 A）**
- 生成规则：`lang: zh` 的文章只生成 `/zh/blog/<slug>/`；`lang: en` 只生成 `/blog/<slug>/`。
- 保留非规范路径但加 `<meta name="robots" content="noindex">`，`canonical` 指向规范路径，sitemap 排除。理由：GitHub Pages 无 301，硬删会让已有外链 404。
- `hreflang` 仅在存在 `translationOf` 对应版本时输出；否则只输出自身语言。语言切换器在无译文时显示"暂无英文版"文本，不渲染链接。
- 两个列表页按 `lang` 过滤，计数文案随之变化。
- `/rss.xml` 只含 `en`，新增 `/zh/rss.xml` 只含 `zh`，`<language>` 分别正确。
- 搜索页按语言限定索引范围（与 E5 的 `data-pagefind-filter` 共用实现）。

**验收标准**
- `dist/zh/blog/<en-slug>/` 存在时带 `noindex` 且 canonical 指向 `/blog/<en-slug>/`。
- 中文文章的英文路径不再出现在 sitemap。
- `npm run verify` 新增断言：sitemap 中不存在语言的规范路径与文章 `lang` 不匹配的 URL。
- 语言切换器在无译文时点击无跳转、读屏可读出"暂无英文版"。

**关键假设**
读者确实按语言分流，且英文读者的价值高于"看起来双语"的观感。验证：先修正 2 周，观察 RSS 订阅与外部搜索来源的语言分布；若没有英文读者，后续不必再投入英文翻译。

**工作量**：M（1–2 天）

### 3. 论文笔记 ↔ 论文条目：把 9 篇论文变成博客入口

**一句话**：让每篇 `paper-reading` 笔记声明它对应的论文，笔记页展示 DOI / 期刊 / BibTeX，论文列表反向出现"笔记"链接。

**为什么选**
这是这个站区别于普通技术博客的唯一结构性优势：已经有 9 篇论文（含中科院分区、DOI）与 7 个项目，却没有一个字解释它们"解决了什么问题、我为什么这么做"。招聘方看论文标题只能看到结论，看不到思考过程；而思考过程恰恰是博客该承载的。

同时它解决"写什么"的冷启动：不需要凭空想选题，把已发表论文的取舍写出来即可。

**范围**
- `blogSchema` 增加 `paper: string`（DOI 或 publications 的 id）。
- 复用 `validateRelations` 的模式：解析不到即抛错阻断构建，错误信息指出文件与字段。
- 笔记页展示论文标题、venue、DOI 外链、BibTeX 复制（复用 `BibtexButton`）。
- 论文列表与首页条目：有笔记时追加"笔记"链接。
- `paper-reading` 分类页按论文年份排序，而非写作日期。

**不做**
自动抓取论文全文、AI 生成摘要、把 DOI 解析结果写进内容（避免未经核实的事实混入）。

**验收标准**
- 写错 DOI 时 `npm run build` 失败并指出 `src/content/blog/<slug>.md`。
- 9 篇论文中至少 1 篇在 publications 列表出现笔记入口。
- 笔记页的 BibTeX 能直接粘贴进 Zotero/LaTeX 并通过编译。

**关键假设**
9 篇论文中至少有 3 篇适合公开写笔记（不涉及未发表数据、导师/企业限制）。验证：先列出 3 篇候选并确认可公开范围；若不足 3 篇，此项降级为"仅关联，不承诺数量"。

**工作量**：M（1 天，不含写作）

---

### 4. 技术写作渲染能力：公式、图、可读的代码

**一句话**：补齐 KaTeX 公式、Mermaid 图表与代码块元信息，让时序、LLM、论文阅读三类选题能写到应有的深度。

**为什么选**
站点的 8 个分类里有 3 个天然需要公式（time-series、llm-engineering、paper-reading）。目前写一个 ARIMA 或 attention 的推导，只能用图片或纯文字近似——这会让文章看起来像"读后感"而不是"技术笔记"。这不是锦上添花，是选题边界。

**范围**
- `remark-math` + `rehype-katex`，KaTeX CSS 打包进 `dist/_astro`，零外链；行内与块级公式在亮/暗主题下都可读。
- Mermaid：优先**构建期**渲染成内联 SVG（保持零客户端依赖）；若图表数量导致构建时间不可接受，再改为单篇按需加载（≤ 30KB gzip）。
- 代码块：支持 `title="src/lib/posts.ts"` 与行高亮；标题栏显示文件名；超过 40 行默认折叠（与 D4 合并）。
- 修正 `.prose { overflow-wrap: anywhere }` 为 `break-word`，避免英文单词被任意截断。

**验收标准**
- 一篇同时含 3 个公式、1 张流程图、1 个带文件名的代码块的文章构建通过。
- 断网后公式与图表仍正确渲染。
- 375px 宽度下无横向溢出，代码块可横向滚动且有视觉提示。

**关键假设**
目标读者会读公式，而不是只看结论。验证：发布 1 篇带公式的文章后，看是否有人引用其中具体公式（外链/评论）；若无人读，则公式能力降级为"能显示即可"，不再投入图表主题适配。

**工作量**：M（1–2 天）

### 5. 正文链接门禁：构建成功不等于页面可用

**一句话**：在 `npm run verify` 中解析构建产物的站内链接、锚点与本地资源，任何一处指向不存在的东西就阻断发布。

**为什么选**
站点已经有 16 个可交叉引用的条目（9 论文 + 7 项目），一旦开始互相引用，手写 slug 出错是必然事件。现有的 `verify-build.mjs` 全是"字符串计数"级断言（卡片数、标签页数、RSS 是否有 item），覆盖不到链接层；而 `validateRelations` 只保护 frontmatter 里的关系，保护不了正文里手写的 `[见这里](/blog/xxx/)`。

**范围**
- 解析 `dist/**/*.html` 的 `href`/`src`：
  - 站内链接 → 对应 `index.html` 或文件存在；
  - 带 `#fragment` → 目标 HTML 中存在该 `id`；
  - `public/` 资源 → 文件存在。
- 失败时输出源 Markdown 文件与坏链接（通过 slug 与标题回查定位）。
- 外链不联网校验；如需，单独 CI job，避免网络抖动导致构建不稳定。
- 顺带修正：`verify-build` 的博文枚举补上 `.mdx`，与内容集合 glob 对齐。

**验收标准**
- 故意写 `[x](/blog/not-exist/)` 与 `#missing-heading`，`npm run verify` 失败并指出位置。
- 现有站点在修正前全部通过（说明门禁没有误报）。
- 检查耗时增量 < 2 秒。

**关键假设**
站内链接会随文章增加而变多，且作者不会手动点击每一条。验证：统计当前正文与组件生成的站内链接数量；若长期 < 10 条，此项可延后到第 10 篇文章。

**工作量**：S（0.5–1 天）

## 6. 明确不做

| 不做 | 理由 |
| --- | --- |
| 评论系统 | 静态站必须引入第三方；1 篇文时维护成本高于收益。替代：文末固定"勘误 / 讨论"入口指向 GitHub Discussions，零后端。 |
| 访问统计 | 无后端，第三方脚本违反现有"零 CDN、零运行时框架"的决策；且个人博客的流量不足以支撑决策。 |
| Newsletter | 没有稳定更新节奏前，订阅列表是负债（答应读者定期发，然后停更）。 |
| PWA / 离线 | 技术博客的离线需求是伪需求——代码要在本机跑，读者不会在地铁里读 API 文档。 |
| 自动翻译 | 机翻会直接摧毁"专业可信"这一唯一资产；宁可显式显示"暂无英文版"。 |
| 客户端框架 / SPA | 与现有构建策略冲突，收益无法证明。 |

## 8. 需要你决定的 4 件事

1. **非规范语言路径怎么处理**：`noindex` 保留（兼容旧链接，推荐），还是完全不生成（更干净，但外链会 404）？
2. **是否接受 Mermaid 的客户端成本**：坚持零运行时（构建期渲染）还是允许单篇按需加载 ~30KB？
3. **论文笔记的公开边界**：只写已发表论文，还是包含在投/企业内部数据？
4. **更新节奏**：每月 1 篇长文，还是双周 1 篇短笔记？这决定 `#1` 是做成轻量脚本还是带模板骨架。
